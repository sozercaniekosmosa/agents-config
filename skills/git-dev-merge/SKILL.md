# Навык `git-dev-merge`

Пошаговый регламент безопасного подтягивания изменений из `origin/develop` в рабочую ветку с обязательным прохождением Quality Gate.

---

## 📍 Шаг 1: Определение целевой ветки и получение обновлений

1. **Определение целевой ветки (`<target_branch>`)**:
   - Если в сообщении пользователя явно указана ветка (например, `/git-dev-merge feature/691-name`, `накати develop на feature/691-name`):
     - Получить текущую ветку: `git branch --show-current`.
     - Если текущая ветка отличается от указанной:
       - Проверить чистоту рабочего дерева (`git status --short`). Если есть незакоммиченные файлы → предложить `git stash` или коммит.
       - Переключиться на указанную ветку:
         ```powershell
         git checkout <target_branch>
         ```
   - Если ветка в запросе не указана — целевой веткой считается **текущая активная ветка**.

2. **Проверка чистоты рабочего дерева**:
   ```powershell
   git status --short
   ```
   - Если есть незакоммиченные файлы → предложить пользователю сохранить их (`git stash`) либо закоммитить перед продолжением.

3. **Получение обновлений develop**:
   ```powershell
   git fetch origin develop
   ```

4. **Проверка входящих коммитов**:
   ```powershell
   git log HEAD..origin/develop --oneline
   ```
   - Если коммитов нет: вывести сообщение *"Ветка develop не содержит новых изменений относительно ветки `<target_branch>`"* и завершить выполнение.
   - Если новые коммиты есть: вывести их список в чат.

---

## 📍 Шаг 2: Выбор стратегии накатывания изменений

Вывести в чат запрос на подтверждение стратегии:

```markdown
[CFON] Шаг 2/4. Выбор стратегии синхронизации с develop

**Целевая ветка:** `<target_branch>`
**Входящие коммиты из develop:**
<список_коммитов>

---

**Выберите стратегию:**
- **[Вариант 1] (Рекомендуется)**: `rebase` (`git rebase origin/develop`) — сохраняет линейную историю без merge-коммитов.
- **[Вариант 2]**: `merge` (`git merge origin/develop`) — классическое слияние с merge-коммитом.
```

- При выборе `rebase`: выполнить `git rebase origin/develop`.
- При выборе `merge`: выполнить `git merge origin/develop`.
- При возникновении конфликтов: остановиться, локализовать конфликтные файлы и предложить варианты разрешения.

---

## 📍 Шаг 3: Автоматический запуск Quality Gate

ОБЯЗАТЕЛЬНО запустить проверки интеграции:

1. **Проверка типов TypeScript**:
   ```powershell
   npx tsc --noEmit
   ```
2. **Проверка FSD-архитектуры**:
   ```powershell
   npm run fsd
   ```
3. **Проверка кросс-модульных зависимостей (Dependency Cruiser)**:
   ```powershell
   npm run check:deps
   ```
4. **Архитектурные unit-тесты**:
   ```powershell
   npx vitest run src/test/architecture.test.ts
   ```
5. **Целевые тесты затронутых модулей** (при необходимости):
   ```powershell
   npx vitest run <path_to_tests>
   ```

Если любая из проверок завершилась с ошибкой — остановиться, вывести диагностику и исправить проблему до отправки в удаленный репозиторий.

---

## 📍 Шаг 4: Выбор действия по отправке изменений в удаленный репозиторий

Вывести в чат интерактивный запрос на выбор действия:

```markdown
[CFON] Шаг 4/4. Выбор действия по отправке изменений

**Целевая ветка:** `<target_branch>`
**Статус проверок Quality Gate:** ✅ Все проверки пройдены

---

**Выберите действие:**
- **[Вариант 1] (Прямой пуш)**:
  - При rebase: `git push origin <target_branch> --force-with-lease`
  - При merge: `git push origin <target_branch>`
- **[Вариант 2] (Amend + Force Push)**:
  `git commit --amend --no-edit` + `git push origin <target_branch> --force-with-lease`
  (поджимает изменения в последний коммит ветки и обновляет удаленную ветку)
- **[Вариант 3] (Не отправлять)**:
  Оставить изменения локально без пуша в удаленный репозиторий.
```

- При выборе **Варианта 1**: выполнить соответствующую команду пуша.
- При выборе **Варианта 2**: выполнить `git commit --amend --no-edit` и затем `git push origin <target_branch> --force-with-lease`.
- При выборе **Варианта 3**: завершить сценарий с выводом информации о локальном состоянии.
- После успешного пуша уведомить пользователя об автоматическом обновлении открытого PR.

## 🔄 Петля Эволюции Навыка (Feedback Loop)

1. **Цель**: Непрерывное поддержание актуальности шагов синхронизации ветки `develop` и инструментов проверки проекта (FSD, dependency cruiser, линтеры).
2. **Ответственность Агента**:
   - При изменении скриптов в `package.json` (например, появление новых линтеров архитектуры или смена флагов `depcruise` / `steiger`) агент обязан предложить обновить Шаг 3 регламента.
   - Логировать выполнение и эволюцию навыка через `node .agents/skills/observer/scripts/observer.cjs --log-history git-dev-merge [trigger] [improvement]`.
