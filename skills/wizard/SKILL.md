# Мастер карточки: контракт и протокол изменений

> [!IMPORTANT]
> Правка Мастера начинается с `check` и `references/contracts.md`, заканчивается `--update`.
> Собственную спецификацию навык обновляет сам (`state.json`, AUTO-блок, `CHANGELOG.md`, `contracts.md`, `guide.md`, лог observer) — без уведомления и без подтверждения.
> Вопрос пользователю — только по пунктам эскалации из раздела «Автономия и эскалация».

## Назначение

- Одна точка правды: что где лежит, что нельзя ломать, чем проверять, как расширять.
- Детектор дрейфа: baseline `state/state.json` → `--check` показывает, что менялось с последней синхронизации.
- Самообновление: `--update` пересчитывает AUTO-блок этого файла, состояние и дописывает строку в `CHANGELOG.md`.
- Цель: любое изменение Мастера проходит один и тот же протокол и не ломает контракт соседних слоёв.

## Автономия и эскалация

> Прямое указание пользователя: навык обновляет себя сам, без уведомлений. Подтверждения — только для спорных случаев, которые навык не может решить по контракту.

### Автономно (без вопроса и без паузы)

- Полный цикл в одном проходе: `--check` → diff → правки → гейты → `--update` → `contracts.md` / `guide.md` / CHANGELOG / лог observer.
- Дрейф при входе — работа, а не вопрос: прочитать `git diff` по путям Мастера, обновить контракт, закрыть `--update`.
- Правка только спецификации (этот файл, `references/`, `CHANGELOG.md`) — гейты кода не нужны, достаточно `--update`.
- Гейты `src/**` (`tsc`, `arch:check`, `wizard:*`, `build`) — если затронут код Мастера; красный гейт чинится без вопроса, пока причина выводится из контракта.
- Новая ловушка, рецепт, инвариант или устаревшая формулировка — правка сразу, без «обновить навык?».
- Порядок применения правил: прямое указание пользователя → правила проекта → этот протокол. Автономия выдана пользователем для зоны Мастера и не расширяет права за её пределы (AGENTS.md не меняется).

### Эскалация (стоп, один вопрос, до ответа — только read-only)

- Публичный контракт меняется так, что ломаются соседние слои, профили или чтение legacy-сессий.
- Поведение неоднозначно: два варианта равно соответствуют правилам, а выбор меняет UX или данные.
- Меняется golden baseline или иной эталон проверок.
- Деструктивные операции с данными (сброс/удаление сессий, миграция legacy).
- Гейт красный, причина не выводится из контракта (не «долго», а «непонятно»).
- Требуется обойти жёсткий инвариант или архитектурное правило (LOC, слои, ACL).
- Правила проекта конфликтуют между собой и прямое указание пользователя приоритет не задаёт.

Формат эскалации: 1 вопрос · варианты · рекомендация · последствие выбора.

## Протокол изменения Мастера

### 1. Вход (до правок)

1. `track.cjs` → дрейф: прочитать `git diff` по путям Мастера и последние строки `CHANGELOG.md`, затем продолжить (дрейф — работа, не повод спрашивать).
2. Прочитать `references/contracts.md`: инварианты, слои, ловушки.
3. Определить затронутые слои: `shared → ai → store → components → db (сессия) + tests`.
4. Классифицировать правку: автономная или эскалационная (раздел «Автономия и эскалация»).

### 2. Проектирование

- Смена поведения = смена контракта? Определить: тип/схема/профиль/промпт/состояние/текст UI.
- Детерминированный слой (engine, review, options, dialogue) — без ИИ; ИИ только там, где нужен смысл.
- Новое поле сессии → `.default(...)` в Zod + тест разбора legacy JSON (старые сессии обязаны читаться).
- Новый текст UI → `profile.ui` + default в `ui.ts`; профиль без поля обязан работать.
- Новый профиль → `profiles/<name>.ts` + `WIZARD_PROFILES` + ветка mock + smoke-сценарий.

### 3. Реализация по слоям

- `shared`: чистые функции, никаких импортов из store/ai/db/components (Leaf Rule).
- `ai`: типы запроса/результата → JSON-схема → промпт с `{{TAGS}}` → сервис с валидацией и русскими ошибками.
- `store`: действие + `rememberUndo` для разрушающих + `dialogueRevision + 1` + `check: null` + persist.
- `components`: только props/callbacks, без прямых обращений к store/db; тексты — из профиля.
- `db`: только JSON-сессия; миграции не нужны, пока схема даёт default.

### 4. Верификация (гейты, по возрастанию)

Запуск автономный при правке кода Мастера; правка только спецификации гейтов не требует.

1. `npx tsc -b`
2. `npm run arch:check`
3. `npm run wizard:review` — перевыбор варианта, факт-чекинг, инвалидация.
4. `npm run wizard:options` — правка/удаление/добавление вариантов.
5. `npm run wizard:elements` — детерминированный слой: поштучный сбор счётных слотов и гид по актам (интро, меню, переходы, факт ответа, mock-вопрос).
6. `npm run wizard:dialogue` — усечение ветки, отмена, черновик.
7. `npm run wizard:golden` — промпты/факты/прогресс/текст; baseline меняется только осознанно.
8. `npm run wizard:scene-smoke` — профиль сцены.
9. `npm run wizard:profiles` — все профили реестра: матчинг, слоты, разделы, счётчики, промпты, итог, UI-тексты.
10. `npm run build` — финальный.
11. UI-ветки — mock-прогон в браузере: `localStorage['studiobook_ai_mock_mode'] = 'true'`.

### 5. Синхронизация навыка (автоматически, в том же проходе)

1. `node .agents/skills/wizard/scripts/track.cjs --update "<что изменилось>"` — всегда, без вопроса.
2. Контракт изменился → `references/contracts.md` (инварианты/поля/ловушки) — сразу.
3. `guide.md` затронутых модулей — сразу (правило проекта).
4. Обход правил (например, файл > 500 LOC) → строка в `docs/techdebt.md` — сразу.
5. Лог эволюции: `node .agents/skills/observer/scripts/observer.cjs --log-history <scope> <trigger> <improvement>` — сразу, без подтверждения.
6. Появился спорный пункт → стоп по разделу «Автономия и эскалация»; спецификация не «додумывается».

### 6. Петля эволюции

- Новый класс поломки → `references/contracts.md` («Ловушки») + строка в CHANGELOG — в том же проходе.
- Изменение процесса проверок → правка списка гейтов в этом файле.
- Устаревший инвариант → удалить/переформулировать, не копить дубли.
- Спорный пункт (см. «Автономия и эскалация») → вопрос, а не тихая правка; после ответа — снова полный цикл.

## Жёсткие инварианты

1. Лента сообщений — единственный источник истины; факты выводятся только replay `collectWizardFacts`.
2. Любое изменение диалога → `dialogueRevision + 1`; черновик валиден только при `draftRevision === dialogueRevision`.
3. Проверка согласованности привязана к ревизии: устаревшая не показывается и не инвалидирует.
4. Разрушающие действия (правка, удаление ветки, инвалидация, сброс) → `rememberUndo` + `undo`.
5. Перевыбор варианта заменяет ответ на месте, ветка сохраняется; факт слота лечится детерминированно.
6. Инвалидация невалидных ответов — только по кнопке, никогда автоматически.
7. Сессия — JSON-блоб `card_wizard_sessions(profile_id, node_id)`; новые поля только с default; legacy `plot_wizard_sessions` только чтение.
8. Слои: `components → store → ai/fs → db → shared`; `shared` — листовой.
9. Промпт-контракт: JSON-схема + строгий разбор; невалидный JSON = ошибка запроса, не «всё ок».
10. Тексты UI — через профиль с дефолтом в `ui.ts`; ни один профиль не обязан задавать всё.
11. Вопрос не повторяет уже заданный: дословный или близкий повтор подменяется детерминированно (`guardWizardRepeatedQuestion`); уточнение по тому же слоту другой формулировкой разрешено.
12. К вопросу — не меньше 6 готовых вариантов (`WIZARD_SUGGESTIONS_MIN = 6`); верхней границы и предела панели нет — список не обрезается, добавление идёт порцией `WIZARD_OPTIONS_BATCH = 5`. Вариант — только ответ автора: запрет ремарок о замысле в промптах шага/вариантов/фокуса и детерминированное снятие хвоста (`stripWizardAnswerAside` внутри `cleanModelText`).
13. Гид по актам (`profile.guided`): меню акта строится детерминированно из `guided.topics`, а порядок пунктов задаёт важность — группа `menuPriority`, внутри группы позиция раздела в этой группе; пункт меню — навигация, а не факт. Ответ на вопрос раздела фиксируется как ОДИН элемент этого раздела без второго запроса к модели; текущий акт выводится из `actIndex` ленты, поэтому правка ветки/undo отматывает гид. Переход по актам закрыт, пока не собран минимум текущего акта (`guided.actMinimum`, нет поля — первая группа `menuPriority`): disabled-чип меню и отказ действия стора считают ОДИН гейт `wizardActGate`/`isWizardActGateOpen`, раздел считается разобранным по значению карточки или ответу автора. «Переходим к следующему акту-арки» ведёт к следующему акту проекта/арки, на последнем — «Завершить сбор». Профиль без количественных слотов не выводит блоки количества в промпты.

## Ловушки

- Правка `src/**` при запущенном Vite dev → EBUSY на temp-файлах редактора крашит watcher: останавливать dev-сервер до правок.
- `countWizardLaterAnswers` и `collectWizardConflicts` якорятся на индекс ОТВЕТА, не вопроса: сам заменяемый ответ не считается поздним.
- Новый тег запроса или промпт → обновить mock-ветку `src/ai/mockMode.ts` и golden baseline, иначе `wizard:golden`/UI расходятся.
- Лимит вариантов — контракт трёх мест сразу: `INTERVIEW_PRINCIPLES`/`WIZARD_STEP_CONTRACT` фабрики, собственные `stepSystem`/`steerTask` профилей (`plotShort`, `sceneShort`) и mock-пулы; правишь одно — проверь `wizard:options` (не меньше 6 во всех профилях).
- `guardWizardRepeatedQuestion` работает только в ANSWER: в STEER повтор текущего вопроса — требование протокола (автор ждёт его после ответа на встречный вопрос).
- Меню акта и вопрос по разделу — разные реплики: меню (`menu: true`) не попадает в «спрошено/отвечено» и не даёт фактов; ответ автора на вопрос раздела фиксируется детерминированно по `questionSlot`, поэтому второй вызов модели для извлечения фактов не нужен и даёт дубль.
- Меню содержит ТОЛЬКО разделы: переход к следующему акту — отдельный чип (`resolveWizardActAction`), а не пункт списка; `next-act`/`finish` в `menuKeys` остаются только у legacy-реплик. Ключи меню без `menuKeys` выводятся по подписи раздела, а не по порядку `guided.topics`: с сортировкой по важности позиция перестала совпадать с хронологией.
- `tsc`: `TS1068` — запятая после метода класса (копия объектного синтаксиса).
- Build на Windows: системный TEMP может дать `Access is denied` → `$env:TEMP` в `.tmp/vite-temp`.
- Файл > 500 LOC — долг: стор и `guided` уже разнесены по модулям (`store/cardWizard/*`, `shared/cardWizard/guided/*`), крупнейший файл Мастера — тестовый `scripts/wizard-golden/profiles.ts`; новые правки не должны переваливать лимит.
- Метка приоритета — ЦВЕТ, не число: UI-тексты (`WIZARD_OPTION_PRIORITY_LABELS`/`_HINTS`, `ui.optionPriorityHint`, легенда профиля) не возвращают «1/2/3»; числа остаются только в данных, схеме и промптах, палитра одна на варианты и меню (`emerald-400`/`amber-400`/`slate-500`).
- Гейт перехода по актам — одна функция для UI и стора: в модалке known = `knownSlots` (карточка) + факты ленты; расчёт только по `knownSlots` открывает кнопку там, где стор отказывает. Минимум — исключительно `guided.topics`: `intro`/`closing` переход не держат.
- Порядок меню — данные профиля, а не порядок объявления разделов: внутри группы его задаёт позиция раздела в `menuPriority` (`buildWizardMenuItems`). Сортировка по `guided.topics` даёт «повороты раньше событий» при равных зелёных метках, автор сам угадывает несвойственный ему порядок, а список важности спорит со своим видом: цепочка ядра идёт от основы к надстройке (события → повороты), и первый зелёный ряд несёт бейдж «сначала».
- `wizard:golden` сравнивает `profile.plot_short` из `cardWizard` (`scripts/wizard-golden/capture.ts`), а не legacy `plotWizard`: baseline — `baseline.card-wizard.json`. Legacy-модули `*/plotWizard` держатся ради совместимости чтения и в golden не входят.
- Mock-пулы вариантов — по категории профиля (`plot_short`, `char_*`, `obj_*`, сцена, акт, событие): один сюжетный пул на все мастера даёт персонажу и предмету чужие ответы. `wizard:profiles` прогоняет mock-шаг каждого профиля (JSON, 6+ уникальных вариантов).
- Вариант с ремаркой о замысле («… — так я показываю, в каком тупике он живёт», «(здесь я задаю тон главы)»): карточка хранит описание, а не объяснение приёма, и выбранный вариант уходит в раздел целиком. Лечится триадой, а не переписыванием ответов автора: запрет в промптах вариантов, снятие хвоста в нормализации текста модели, проверка в гейте вариантов. Срезается только фрагмент с меткой приёма, ремесленным глаголом и голосом автора/читателя — обычное тире в тексте остаётся.

## Границы

- `--check/--report/--audit` — read-only; `--update` пишет только: `state/state.json`, AUTO-блок `SKILL.md`, `CHANGELOG.md`.
- Спецификация навыка (`SKILL.md`, `references/contracts.md`, `CHANGELOG.md`, `guide.md`, `docs/techdebt.md`, лог observer) обновляется автономно, в том же проходе, что и правка Мастера.
- Гейты Мастера запускаются автономно при правке кода; `npm run build` — когда затронут прод-путь.
- Навык не подменяет `guide.md`: гайды — статический контекст модулей, здесь — протокол изменений Мастера.
