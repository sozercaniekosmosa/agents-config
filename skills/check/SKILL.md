Анализ кода на соответствие таскам и правилам проекта (Read-Only аудит).
При обнаружении ошибок → формирование отчета со статусами [✓], [!], [✗] и рекомендациями по исправлению (без автоматической модификации кода).

### Флаги запуска:

- `/check --fast` → пропустить тесты (Vitest/Jest/Playwright) (только линт, tsc, архитектурный аудит).
- `/check --full` → принудительный полный аудит проекта (Режим C).

---

## Алгоритм работы

### Шаг 1. Статические технические проверки (TSC, ESLint)

1. **Сохранение файлов**: Перед проверкой убедиться, что все файлы в редакторе сохранены на диск.
2. **TypeScript**: Запустить проверку типов (`npx tsc --noEmit`). При наличии `tsconfig.app.json` → `npx tsc -p tsconfig.app.json --noEmit`.
3. **ESLint**: Выполнить линтинг измененных файлов (`npx eslint` ТОЛЬКО при наличии установленного `eslint` в `package.json` и конфигурационного файла в корне; иначе шаг пропускается).
4. **Обработка сбоев**: При любых статических ошибках/нарушениях линта или типов → зафиксировать ошибки и перейти к **Шагу 3 (Рекомендации)**.

### Шаг 2. Статический архитектурный аудит

1. Выполнить проверку кросс-модульных импортов, изоляции слоев и мертвого кода с помощью скрипта:
   ```bash
   node .agents/skills/check/arch-check.cjs
   ```
2. Выполнить проверку соответствия архитектурным требованиям и стандартам проекта из `docs/` (`docs/project-rules.md`, `docs/architecture.md`, детали в `references/architectural_audit.md`).
3. При любых архитектурных нарушениях или падении скрипта → зафиксировать нарушения и перейти к **Шагу 3 (Рекомендации)**.
4. Выполнить аудит телеметрии и эволюции навыков:
   ```bash
   node .agents/skills/observer/scripts/observer.cjs --audit
   ```
   При наличии рекомендаций `[CREATE]`, `[MODIFY]`, `[DELETE]` → включить их в итоговый отчет.

### Шаг 3. Рекомендации по устранению (Read-Only)

Навык `check` не выполняет автоматическую модификацию кода. При обнаружении ошибок сформировать структурированные рекомендации:

1. **Статические и архитектурные ошибки** (типы TS, линт, DAG, dead code) → предложить пользователю точечное исправление или постановку задачи для `/resolve`.
2. **Рантайм-сбои и сбои тестов** → предложить локализацию и устранение бага через навык `/debug`.

### Шаг 4. Ограничения

- Запуск тестов (Vitest / Jest / Playwright) → строго при их наличии в проекте и с разрешения пользователя.

### Шаг 5. Отчет

Вывод статусов в чат:

- `[✓]` — успешно, ошибок нет.
- `[✗]` — критические ошибки/нарушения.
- `[!]` — некритичные предупреждения.
- Указать рекомендации по устранению ошибок, если они обнаружены.

### Шаг 6. Петля Эволюции Навыка (Feedback Loop)

1. **Анализ сдвига**: Проверить, выявила ли проверка неактуальные правила, расхождения со спецификациями или новые архитектурные паттерны.
2. **Аудит спецификаций**: Запустить `node .agents/skills/guide/scripts/audit-guide.cjs --all` для проверки синхронизации `guide.md`.
3. **Фиксация**: При расхождениях предложить пользователю обновить правила/спецификации (`/learn` или подтверждение в чате).
