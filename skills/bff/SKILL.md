# Навык проектирования BFF (Backend For Frontend)

Навык используется для глубокого анализа работы UI с API, выявления неэффективностей и проектирования универсального слоя BFF, который радикально упрощает клиентский код.

## 1. Правила аудита и поиска узких мест
> [!TIP]
> Агент может автоматически найти техдолг, запустив скрипт: `node .agents/skills/bff/scripts/audit-ui.cjs src/`

При анализе контрактов, кода и эндпоинтов агент обязан:
- **Анализировать весь CRUD-цикл**: Оценивать не только чтение, но и создание, копирование (учитывать специфику глубокого клонирования vs копирования метаданных), обновление и массовое удаление.
- **Искать скрытую оркестрацию**: Выявлять каскады запросов (N+1), ручную фильтрацию лишних данных от бэкенда на клиенте, чанкирование и ручной маппинг стейта.
- **Генерировать реализуемые упрощения**: Искать способы максимального сокращения запросов (View-Model Synthesis). Задавать вопрос: "Как свести весь каскад к одному смарт-запросу, возвращающему готовое UI-дерево/таблицу?".
- **Агностика бэкенда**: Проектировать слой архитектурно абстрактно от стека бэкенда. Фокус исключительно на идеальном контракте взаимодействия UI ↔ BFF.

## 2. Ведение реестра долга (`debt/debt.md`)
Реестр долга отслеживает текущую стадию проработки каждого проблемного модуля UI:
- **Гранулярные статусы задач**:
  - `- [ ]` **Backlog**: проблема выявлена, проектирование еще не начато.
  - `- [~]` **In Review / RFC**: план составлен, идет согласование контракта (указывать ссылку на Confluence RFC).
  - `- [x]` **Backend Ready**: BFF-эндпоинты готовы и развернуты в шлюзе (указывать версию шлюза, напр. `gateway 1.2.1`, и утвержденную страницу Confluence).
  - `- [X]` **Completed in UI**: клиентский код переписан на BFF, старые downstream вызовы удалены (Zero Dead Code).
- **Непрерывное обновление**: при любом согласовании или изменении контракта в Confluence/шлюзе статус в `debt/debt.md` обязан обновляться немедленно.

## 3. Генерация и ведение планов-контрактов (`plans/`)
При команде на создание или актуализацию плана BFF:
1. Файлы планов хранятся в `.agents/skills/bff/plans/`.
2. Имя файла строго: `bff-YYYY-MM-DD-HH-MM-[kebab-name].md`.
3. **Обязательная мета-шапка плана (Статус и связь с источником правды)**:
   ```markdown
   # [Название плана]
   > [!NOTE]
   > - **Статус:** `[DRAFT]` | `[IN_REVIEW]` | `[BACKEND_READY]` | `[COMPLETED]` | `[SUPERSEDED]`
   > - **Версия Backend/Gateway:** например, `gpna-asodu-tech-gateway 1.2.1`
   > - **Спецификация в Confluence:** ID страницы, заголовок и ссылка на RFC
   > - **Дата актуализации:** YYYY-MM-DD
   ```
4. **Правило Continuous Sync (защита от устаревания)**:
   - Если контракт эволюционировал (например, Draft-1 → Draft-2 с разбиением на несколько ручек):
     - План в `plans/` обязан быть актуализирован под утвержденное решение.
     - Либо создается новый план, а старый помечается статусом `[SUPERSEDED / HISTORICAL]` с прямой ссылкой на заменяющий документ.
   - Запрещено оставлять локальные планы в неактуальном состоянии, противоречащем реализации шлюза и Confluence.
5. **Обязательная структура документа**:
   - **1. Анализ узких мест**: 
     - Явное перечисление целевых UI-модулей (какие компоненты и хуки подвергнутся рефакторингу).
     - Явный список текущих downstream API (ручки), которые перестанут вызываться с клиента и уйдут под замену.
     - Разбор технических проблем текущей реализации (костыли, лимиты, дублирование состояния).
   - **2. Проектирование API (Маршрутизация)**: 
     - Выбор архитектурной модели (Smart-Эндпоинт vs Гранулярные ресурсы) с учетом кэширования TanStack Query и возможностей UI-компонентов.
     - Унифицированные и скрывающие бизнес-домен мутации (или фиксация их сохранения через прокси НСИ).
   - **3. Контракты (TypeScript / Zod)**: 
     - **Thin Client**: Идеальный слепок под UI-модель (никаких тяжелых мапперов на фронте).
     - **Полнота DTO**: Обязательное наличие полей пути (`path`), прототипов и метаданных для автономности модалок.
     - **Защита от техдолга (Типизация)**: Использование **Discriminated Unions** (строгие типы по дискриминатору) вместо слаботипизированных `Record<string, unknown>`.
   - **4. Разработка слоя BFF**: 
     - Описание Anti-Corruption Layer (Фасада) для изоляции UI.
     - Обязательный слой **Auth & RBAC**: проброс токенов (Token Relay), фильтрация по правам, контракты 401/403.
     - **Best Practices (на будущее)**: Observability (проброс Correlation ID), строгая валидация входящих payload, поддержка отмены запросов (AbortSignal), автогенерация OpenAPI, Rate Limiting и Health Checks.
   - **5. Интеграция UI**: Шаги по кардинальному сокращению кода клиента (один хук `useQuery`, удаление ручного стейт-менеджмента).
   - **6. Очистка**: Zero Dead Code (удаление старых мапперов и queryOptions).

## 4. Рецензирование драфтов и предложений коллег (BFF Review)

Используется при получении ссылки на страницу Confluence (через навык `/confluence`) или сырого текста предложения коллеги в чате.

### 4.1. Чек-лист архитектурной валидации:
1. **Сверка с реальным UI-кодом (Active Codebase Verification)**:
   - Найти всех потребителей эндпоинта в коде (`useQuery`, `fetchQuery`, мутации, модалки).
   - Проверить полноту полей DTO: хватает ли полей для форм создания, копирования, удаления, хлебных крошек (`meta.path`), тултипов?
   - Искать скрытые тяжелые запросы (например, выгрузка всех сущностей только ради одного `prototypeNodeId`).
2. **Аудит стратегии кэширования (TanStack Query Audit)**:
   - Проверить влияние на кэш: не превращает ли предложение атомарный кэш в монолитный снимок с 100% cache miss на каждый клик?
   - Оценить сетевой оверхед (передача дельты vs повторная перекачка всего графа/дерева).
3. **Совместимость с UI-библиотеками (`@willykit-ui`)**:
   - Проверить поддержку нативного асинхронного `loadData` с локальным спиннером на узле vs полной замены стейта и мерцания дерева.
   - Проверить устойчивость к состояниям гонки (race conditions) при быстрых кликах.
4. **Оценка нагрузки на Backend/Gateway**:
   - Предпочитать плоские запросы O(1) тяжелым in-memory рекурсивным агрегациям графов на шлюзе.
   - Запрашивать у бэкенда только «дешёвые» поля, которые уже нативно есть в БД (например, колонка `path` в НСИ).
5. **Аудит истории версий (Draft Evolution & Ownership)**:
   - Проверить предшествующие черновики (Draft #1, Draft #2): кто автор (`createdBy`), какие решения уже задеплоены в шлюзе.
   - Запрет негласного редактирования чужих страниц в Confluence: рецензии давать через диалог или ADR-статусы.

### 4.2. Стандарт вывода результатов анализа:
1. **Архитектурный вердикт**: четкое обоснование выбора стратегии (гранулярная vs монолитная) через матрицу Trade-offs.
2. **Точечный список доработок DTO**: поля, которых реально не хватает фронтенду, с обоснованием их нулевой стоимости для бэкенда.
3. **Очеловеченный текст для чата**:
   - Лаконичный, разговорный язык разработчиков (без канцеляризмов, длинных тире `—`, избыточной вежливости).
   - Прямой ответ на сомнения и открытые вопросы бэкендера (например, реакция на подсвеченные им риски).
4. **Оформление в Confluence (при необходимости)**:
   - Ведение чистой спецификации (запрет зачёркиваний `<s>` в коде DTO).
   - Фиксация отклонённых альтернатив строго через отдельный блок ADR (Architecture Decision Record).
