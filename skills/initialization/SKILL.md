# Навык Initialization (Инициализация и Синхронизация правил проекта)

Навык решает 2 ключевые задачи:

1. **Синхронизация с центральным репозиторием** (`sozercaniekosmosa/agents-config`): Загрузка (pull) или публикация (push) обновлений навыков и глобальных стандартов.
2. **Интерактивное заполнение правил проекта**: Формирование локальных файлов в `docs/` (`context.md`, `project-rules.md`, `architecture.md`) под текущий проект.

---

## 🚀 Режимы Вызова (Quick Action)

Если пользователь явно указывает команду синхронизации:

1. **Загрузка / Обновление (Pull)**:
   - Вызов: `/initialization pull`, "загрузи", "обнови", "скачай".
   - Действие: Запустить `node .agents/skills/initialization/scripts/sync.cjs pull`
   - Изоляция: Использует локальный git `.agents/.git`, не затрагивая родительский Git проекта. Игнорирует проектные файлы `docs/*`.

2. **Публикация Изменений (Push)**:
   - Вызов: `/initialization push [сообщение коммита]`, "сохрани", "запуш", "опубликуй", "отправь".
   - Действие: Запустить `node .agents/skills/initialization/scripts/sync.cjs push "сообщение"`

3. **Интерактивный Режим (по умолчанию)**:
   - При вызове `/initialization` без аргументов агент задает вопрос пользователя через `ask_question`:
     - Опция 1: `[Интерактивная инициализация правил проекта]` -> перейти к Диалогу Q&A (Этап 1-3).
     - Опция 2: `[Pull: Скачать обновленные навыки и стандарты с GitHub]` -> выполнить `sync.cjs pull`.
     - Опция 3: `[Push: Опубликовать текущие изменения навыков на GitHub]` -> выполнить `sync.cjs push`.

## 🔑 Ключевые Принципы Инициализации

> [!IMPORTANT]
> **Предварительный вывод структуры вопросов**:
> До начала интервью СТРОГО ОБЯЗАТЕЛЬНО вывести пользователю полную структуру предстоящих вопросов и блоков.

> [!IMPORTANT]
> **Интерактивный режим с готовыми вариантами ответов**:
> Для каждого вопроса агент обязан предложить минимум 3 варианта:
> 1. `[Авто-определение]` — вариант на основе сканирования кодовой базы/`package.json`.
> 2. `[Рекомендуемый стандарт]` — проверенное решение для данного типа стека.
> 3. `[Альтернатива / Свой вариант]` — гибкий выбор пользователя.

> [!IMPORTANT]
> **Детерминированный подбор архитектуры (Architecture Decision Engine)**:
> Агент определяет архитектуру на основе `references/architecture_matrix.md`:
> 1. Классифицирует проект по 4 критериям (тип продукта, характер вычислений, потребитель API, модель стейта).
> 2. Сопоставляет с архетипами: `Layered Engine / SDK`, `Feature-Sliced Design (FSD v2)`, `Microkernel + Plugins`, `Hexagonal / Clean Architecture`.
> 3. Обязан аргументировать выбор перед пользователем: обосновать выбранный паттерн и объяснить, почему отброшены альтернативы.
> 4. Строго соблюдать последовательность: Сначала определение архитектуры и слоев (`architecture.md`), затем фиксация технических стандартов под эти слои (`project-rules.md`).

## 📋 Порядок Выполнения Инициализации Rules

### Этап 1: Предварительный анализ и Анонс структуры

1. Сканировать файлы проекта (`package.json`, `tsconfig.json`, структуру `src/`).
2. Вывести дерево вопросов с логической последовательностью (Контекст → Архитектура → Стандарты → Финализация):

```markdown
📋 **План интерактивной инициализации правил проекта**:

1. **Контекст проекта (`context.md`)**:
   - Назначение, суть и границы приложения
   - Технологический стек и окружение

2. **Архитектура и Контракты (`architecture.md`)**:
   - Авто-подбор и аргументация архитектурного паттерна по `architecture_matrix.md`
   - Определение слоев проекта (`src/`) под специфику задачи
   - Направленный граф зависимостей (DAG: правила импортов между слоями)
   - Публичный API и границы изоляции
   - Anti-Corruption Layer (ACL: правила изоляции внешних API/DTO и границы мапперов)

3. **Технические стандарты (`project-rules.md`)**:
   - Правила слоев и модулей (строго синхронизированные с выбранной архитектурой)
   - Стандарты React/TypeScript/Стейта и доменные Best Practices стека
   - Runtime-валидация внешних данных (Zod / Valibot / схемы контрактов)
   - Правила изоляции DTO (мапперы, fallbacks, запрет сырых данных в UI)
   - Политика отслеживания техдолга (`docs/techdebt.md` вместо `// TODO`)
   - Стилизация, дизайн-система и UI-контраст
   - Тестирование

4. **Финализация и Инициализация**:
   - Запись правил в `docs/` по шаблонам
   - Создание базового реестра техдолга `docs/techdebt.md`
   - Разворачивание структуры папок слоев в `src/` с контрактами `index.ts`
   - Предложение инициализации проекта и установки зависимостей
```

3. Запросить подтверждение перехода к диалогу.

---

### Этап 2: Диалог с готовыми вариантами (Q&A)

1. По блоку **Контекст (`context.md`)**: агент собирает назначение, стек и целевую аудиторию проекта.
2. По блоку **Архитектура (`architecture.md`)**:
   - Агент анализирует собранный контекст через `references/architecture_matrix.md`.
   - Предлагает оптимальный архитектурный паттерн с аргументацией ("почему X, а не Y").
   - Предлагает конкретный состав слоев, направленный граф зависимостей (DAG) и состав публичного API (`src/index.ts`).
   - Определяет границы ACL (Anti-Corruption Layer): где трансформируются внешние данные и форматы в доменные модели.
   - Согласовывает архитектурный план с пользователем через `ask_question` / чат.
3. По блоку **Технические стандарты (`project-rules.md`)**:
   - Под согласованную на шаге 2 архитектуру формулирует правила изоляции слоев.
   - Предлагает стек и правила runtime-валидации (Zod / Valibot / встроенные схемы) на границах системы.
   - Формулирует требования ACL: обязательные мапперы DTO → Domain, fallbacks, запрет сырых DTO в UI/компонентах.
   - Фиксирует стандарт ведения техдолга (`docs/techdebt.md`, запрет `// TODO` в коде).
   - Формирует доменные Best Practices стека (Canvas/SVG, WebGL, Zustand, Workers и др.).

---

### Этап 3: Запись файлов по шаблонам

После согласования всех ответов подставить значения в референсные шаблоны:

- `references/context_template.md` → `docs/context.md`
- `references/architecture_template.md` → `docs/architecture.md` (подставить выбранный паттерн, доменные слои, DAG зависимостей, публичные контракты и границы ACL)
- `references/project_rules_template.md` → `docs/project-rules.md` (подставить правила слоев согласно архитектуре, стек валидации, правила ACL и лучшие практики стека)
- Инициализировать `docs/techdebt.md` (если еще не создан).

---

### Этап 4: Разворачивание архитектуры, Инициализация и Зависимости

После сбора всех данных и успешной записи файлов правил:
1. **Авто-создание структуры архитектуры**:
   - На основе согласованных слоев из `architecture.md` создать соответствующие директории в `src/` с начальными файлами контрактов `index.ts` (запрещено хардкодить статичные наборы папок).
   - При наличии внешних контрактов/API подготовить директории для валидаторов/мапперов (ACL).
   - Создать базовый `docs/techdebt.md` при его отсутствии.
2. **Инициализация каркаса и установка зависимостей**:
   - Проверить наличие базового каркаса (`App.tsx` / `main.tsx`) и предложить развернуть его при отсутствии.
   - Предложить пользователю установить зависимости (выполнив `npm install`, `pnpm install` или аналог).
3. **Согласование**: запросить у пользователя явное подтверждение перед запуском команд установки.
