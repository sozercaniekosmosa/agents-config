# Навык Initialization (Инициализация и Синхронизация правил проекта)

Навык решает 2 ключевые задачи:

1. **Синхронизация с центральным репозиторием** (`sozercaniekosmosa/agents-config`): Загрузка (pull) или публикация (push) обновлений навыков и глобальных стандартов.
2. **Интерактивное заполнение правил проекта**: Формирование локальных файлов в `docs/` (`context.md`, `project-rules.md`, `architecture.md`) под текущий проект.

---

## 🚀 Режимы Вызова (Quick Action)

Если пользователь явно указывает команду синхронизации:

1. **Загрузка / Обновление (Pull)**:
   - Вызов: `/initialization pull`, "загрузи", "обнови", "скачай".
   - Действие: Запустить `node .agents/skills/initialization/scripts/sync.cjs pull`
   - Изоляция: Использует локальный git `.agents/.git`, не затрагивая родительский Git проекта. Игнорирует проектные файлы `docs/*`.

2. **Публикация Изменений (Push)**:
   - Вызов: `/initialization push [сообщение коммита]`, "сохрани", "запуш", "опубликуй", "отправь".
   - Действие: Запустить `node .agents/skills/initialization/scripts/sync.cjs push "сообщение"`

3. **Интерактивный Режим (по умолчанию)**:
   - При вызове `/initialization` без аргументов агент задает вопрос пользователя через `ask_question`:
     - Опция 1: `[Интерактивная инициализация правил проекта]` -> перейти к Диалогу Q&A (Этап 1-3).
     - Опция 2: `[Pull: Скачать обновленные навыки и стандарты с GitHub]` -> выполнить `sync.cjs pull`.
     - Опция 3: `[Push: Опубликовать текущие изменения навыков на GitHub]` -> выполнить `sync.cjs push`.

## 🔑 Ключевые Принципы Инициализации

> [!IMPORTANT]
> **Предварительный вывод структуры вопросов**:
> До начала интервью СТРОГО ОБЯЗАТЕЛЬНО вывести пользователю полную структуру предстоящих вопросов и блоков.

> [!IMPORTANT]
> **Интерактивный режим с готовыми вариантами ответов**:
> Для каждого вопроса агент обязан предложить минимум 3 варианта:
> 1. `[Авто-определение]` — вариант на основе сканирования кодовой базы/`package.json`.
> 2. `[Рекомендуемый стандарт]` — проверенное решение для данного типа стека.
> 3. `[Альтернатива / Свой вариант]` — гибкий выбор пользователя.

> [!IMPORTANT]
> **Детерминированный подбор архитектуры (Architecture Decision Engine)**:
> Агент определяет архитектуру на основе `references/architecture_matrix.md`:
> 1. Классифицирует проект по 4 критериям (тип продукта, характер вычислений, потребитель API, модель стейта).
> 2. Сопоставляет с архетипами: `Layered Engine / SDK`, `Feature-Sliced Design (FSD v2)`, `Microkernel + Plugins`, `Hexagonal / Clean Architecture`.
> 3. Обязан аргументировать выбор перед пользователем: обосновать выбранный паттерн и объяснить, почему отброшены альтернативы.
> 4. Строго соблюдать последовательность: Сначала определение архитектуры и слоев (`architecture.md`), затем фиксация технических стандартов под эти слои (`project-rules.md`).

> [!IMPORTANT]
> **Тотальная борьба с Coupling и максимизация Cohesion**:
> Агент обязан внедрять в `architecture.md` и `project-rules.md` бескомпромиссные правила:
> 1. **Low Coupling**: Закон Деметры, инверсия зависимостей (DIP), 0 cross-imports между соседними модулями/плагинами, запрет глубоких импортов в обход `index.ts`, изоляция платформенного окружения.
> 2. **High Cohesion**: Single Responsibility Principle (SRP), функциональная связность (полная инкапсуляция схем, UI и логики модуля в своей папке), запрет God Objects и монолитных утилит/сторов.

## 📋 Порядок Выполнения Инициализации Rules

### Этап 1: Предварительный анализ и Анонс структуры

1. Сканировать файлы проекта (`package.json`, `tsconfig.json`, структуру `src/`).
2. Вывести пользователю план интерактивной инициализации строго по шаблону `references/interview_structure.md` (Раздел 1).
3. Запросить подтверждение перехода к диалогу.

---

### Этап 2: Диалог с готовыми вариантами (Q&A)

Провести интервью строго по сценарию `references/interview_structure.md` (Раздел 2):
1. **Контекст (`context.md`)**: собрать назначение, стек и целевую аудиторию проекта.
2. **Архитектура (`architecture.md`)**:
   - Подобрать архетип по `references/architecture_matrix.md` с аргументацией и отброшенными альтернативами.
   - Определить состав слоев, правила DAG и публичный контракт (`src/index.ts`).
   - Зафиксировать принципы Low Coupling (DIP, Закон Деметры, запрет cross-imports и deep imports).
   - Определить границы ACL и точки валидации (включая манифесты плагинов / внешние DTO).
   - Согласовать архитектурный план с пользователем через `ask_question` / чат.
3. **Технические стандарты (`project-rules.md`)**:
   - Сформулировать правила изоляции слоев под выбранную архитектуру.
   - Зафиксировать стандарты Low Coupling & High Cohesion (SRP, функциональная связность, запрет God Objects / монолитных утилит).
   - Зафиксировать стек runtime-валидации (Zod / Valibot), правила мапперов ACL и fallbacks.
   - Зафиксировать политику техдолга (`docs/techdebt.md`, запрет `// TODO` в коде) и доменные Best Practices стека.

---

### Этап 3: Запись файлов по шаблонам

После согласования всех ответов подставить значения в референсные шаблоны:

- `references/context_template.md` → `docs/context.md`
- `references/architecture_template.md` → `docs/architecture.md` (паттерн, слои, DAG, публичные контракты, принципы Low Coupling/High Cohesion, границы ACL)
- `references/project_rules_template.md` → `docs/project-rules.md` (правила слоев, стандарты Low Coupling/High Cohesion, стек валидации, правила ACL, лучшие практики стека)
- Инициализировать `docs/techdebt.md` (если еще не создан).

---

### Этап 4: Разворачивание архитектуры, Инициализация и Зависимости

После сбора всех данных и успешной записи файлов правил выполнить генерацию строго по `references/scaffolding_guide.md`:
1. **Генерация слоев и контрактов**:
   - Создать директории слоев на основе `architecture.md` с начальными контрактами `index.ts`.
   - Развернуть специфичную инфраструктуру под выбранный архетип по `references/scaffolding_guide.md` (для Microkernel: `src/kernel/index.ts` с Zod-манифестом, папка `src/plugins/` с эталонным плагином и локальной `schema.ts`, добавление `zod` в `package.json`).
   - Создать базовый `docs/techdebt.md` при его отсутствии.
2. **Инициализация каркаса и установка зависимостей**:
   - Проверить наличие точки входа (`App.tsx` / `main.tsx`) и предложить развернуть ее при отсутствии.
   - Запросить у пользователя подтверждение и запустить установку зависимостей (`npm install`).
