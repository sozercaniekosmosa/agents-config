# Матрица Архитектурных Паттернов и Критериев Выбора (Architecture Match Matrix)

Справочник для навыка `initialization`. Используется для детерминированного подбора архитектуры, структуры папок и правил зависимостей под домен проекта.

---

## 🎯 1. Алгоритм Подбора Архитектуры (Decision Flow)

При инициализации агент анализирует вводные данные из `context.md` по 4 критериям:

| Критерий | Вариант A | Вариант B | Вариант C |
| :--- | :--- | :--- | :--- |
| **1. Тип продукта** | Web App / SPA / SaaS | Library / SDK / Engine / Canvas | Plugin Platform / Расширяемая система |
| **2. Доменная специфика** | Бизнес-формы, CRUD, роутинг | Математика, рендеринг, сериализация схемы | Модульные расширения, слабая связанность |
| **3. Потребитель** | Конечный пользователь (UI) | Внешний разработчик (Public API) | Ядро системы через контракты плагинов |
| **4. Стейт & Данные** | Серверный кэш, UI-стейт форм | Рантайм-граф/сцена, история undo/redo, viewport | Изолированный стейт плагинов, шина сообщений |
| **ИТОГОВЫЙ ПАТТЕРН** | **Feature-Sliced Design (FSD v2)** | **Layered Engine / SDK** | **Microkernel + Plugins (Capability)** |

*(Если проект — CLI / Node.js утилита / бэкенд без UI → выбирается **Hexagonal / Clean Architecture**).*

## 🏛️ 2. Спецификации Архитектурных Архетипов

### Архетип 1: Layered Engine / SDK
- **Назначение**: библиотеки компонентов, графические редакторы (SVG, Canvas, WebGL), вычислительные ядра, SDK для внешних интеграторов.
- **Ключевой принцип**: полное отделение математики и схемы данных от UI-фреймворка (React) и DOM.
- **Слои (`src/`)**:
  1. `core/`: чистый TypeScript (векторы, матрицы, сплайны, алгоритмы пересечений). 0 зависимостей от React/DOM.
  2. `schema/`: контракты формата хранения/сериализации (`types.ts`, `serializer.ts`, валидаторы, миграции версий). 0 зависимостей от React/DOM.
  3. `model/` (или `domain/`): рантайм-модели сущностей (узлы, ребра, реестры фабрик компонентов).
  4. `store/`: управление состоянием (undo/redo, selections, viewport scale/pan, режимы edit/view).
  5. `canvas/` (или `viewport/`): сцена рендеринга (SVG/Canvas), контроллеры жестов (pan, zoom, drag-and-drop).
  6. `components/`: UI-обвязка библиотеки (контролы зума, миникарта, палитра, публичные `<GraphEditor />`, `<GraphViewer />`).
  7. `shared/`: общие утилиты, хелперы, базовые хуки.
  8. `demo/` (опционально): изолированный тестовый стенд/playground, потребляющий SDK строго через публичный экспорт `src/index.ts`.
- **Направленный граф зависимостей (DAG)**:
  - `demo` → `components` / `canvas` → `store` → `model` → `schema` → `core` → `shared`.
  - Запрет циклических и обратных импортов (например, `core` или `schema` никогда не импортируют `store` или `canvas`).
- **Публичный контракт (`src/index.ts`)**:
  - Экспорт готовых компонентов, фабрик, хуков доступа к состоянию и типов схемы. Внутренние файлы слоев наружу не торчат.
- **ACL и Валидация**:
  - Слой `schema/` выступает как Anti-Corruption Layer (ACL) для внешних JSON/файлов: валидация схемы на входе/выходе, изоляция внутреннего рантайм-графа от персистентного формата.

### Архетип 2: Feature-Sliced Design (FSD v2)
- **Назначение**: классические веб-приложения, SPA, SaaS-сервисы, порталы со страницами и роутингом.
- **Ключевой принцип**: декомпозиция по ценности для пользователя (фичи) и бизнес-сущностям с жесткой иерархией слоев.
- **Слои (`src/`)**:
  1. `app/`: точка входа, провайдеры контекста, инициализация роутинга, глобальные стили.
  2. `pages/`: маршрутизируемые страницы приложения, композиция виджетов.
  3. `widgets/`: самостоятельные крупные блоки интерфейса (Header, Sidebar, GraphWorkspace).
  4. `features/`: законченные пользовательские сценарии (ExportDiagram, ConnectNodes, ZoomControls).
  5. `entities/`: бизнес-сущности домена (Graph, Project, User) со своими UI, моделью и API.
  6. `shared/`: переиспользуемые UI-компоненты (кнопки, инпуты), утилиты, клиенты API.
- **Направленный граф зависимостей (DAG)**:
  - `app` → `pages` → `widgets` → `features` → `entities` → `shared`.
  - Импорт возможен строго сверху вниз (слой выше импортирует слои ниже). Импорт соседей на одном слое (cross-slice) запрещен без поднятия на слой выше.
- **Сегменты внутри слайсов**:
  - Каждый слайс (`features/export-diagram`, `entities/graph`) делится на сегменты: `ui/`, `model/`, `api/`, `lib/` с публичным `index.ts`.
- **ACL и Валидация**:
  - `shared/api/`: DTO контракты и runtime-схемы валидации ответов (Zod/Valibot).
  - `entities/*/model/` (или `api/`): функции-мапперы (`dtoToDomain`), изолирующие UI/Store от сырых API DTO. Запрет использования сырых `*Dto` в UI-компонентах.

### Архетип 3: Microkernel + Plugins (Capability Pattern)
- **Назначение**: модульные платформы, графические редакторы с экосистемой сторонних плагинов, CAD/DCC инструменты (интеграция с навыками `.agents/skills/contract` и `pak`).
- **Ключевой принцип**: минимальное неизменяемое ядро (микроядро) + изолированные плагины, взаимодействующие строго через спецификации и адаптеры.
- **Слои (`src/`)**:
  1. `kernel/`: жизненный цикл приложения, менеджер регистрации плагинов, шина событий (EventBus), контекст DI.
  2. `contracts/` (или `specs/`): типы контрактов (`CONTRACT_SPEC`), интерфейсы адаптеров, контрактный прокси-валидатор (`wrapWithContractValidator`).
  3. `plugins/`: изолированные папки плагинов. Каждый плагин автономен, имеет `guide.md`, объявляет `CONTRACT_SPEC` и публичный `index.ts`.
  4. `shared/`: общие типы ядра, логгер, базовые утилиты.
- **Направленный граф зависимостей (DAG)**:
  - `plugins` → `contracts` ← `kernel`.
  - Прямое общение между плагинами (`plugin-a` → `plugin-b`) строго запрещено. Взаимодействие только через Pull Discovery адаптеров ядра.
- **ACL и Валидация**:
  - `CONTRACT_SPEC` + `wrapWithContractValidator`: рантайм-валидация аргументов и возвращаемых значений на границе плагин-ядро.
  - Изоляция ядра от некорректного стейта плагинов через fallback-поведение при отсутствии адаптеров.

---

### Архетип 4: Hexagonal / Clean Architecture
- **Назначение**: CLI-утилиты, парсеры, Node.js микросервисы, бэкенд-обработчики.
- **Ключевой принцип**: независимость бизнес-логики от фреймворков, БД, консоли и протоколов ввода-вывода (Ports & Adapters).
- **Слои (`src/`)**:
  1. `domain/`: чистые доменные сущности, фабрики и инварианты.
  2. `use-cases/` (или `application/`): сценарии выполнения, бизнес-транзакции, порты интерфейсов ввода/вывода (Interfaces).
  3. `adapters/`: реализация портов (CLI контроллеры, парсеры аргументов, presenters).
  4. `infrastructure/`: работа с файловой системой (FS), сетью, сторонними библиотеками.
- **Направленный граф зависимостей (DAG)**:
  - `infrastructure` → `adapters` → `use-cases` → `domain` (все стрелки зависимостей направлены строго внутрь к `domain`).
- **ACL и Валидация**:
  - Адаптеры ввода/вывода (`adapters/`) выступают строгим Anti-Corruption Layer: валидируют входящие данные и трансформируют их в доменные структуры до передачи в `use-cases`.

## 📋 3. Требования к формированию Архитектурного Плана агентом

Когда агент выбирает паттерн, он обязан сгенерировать план со следующими элементами:
1. **Название паттерна и аргументация**:
   - Почему выбран данный паттерн под текущую задачу.
   - Почему отброшены другие паттерны (например: *"FSD отброшен, так как библиотека не содержит страниц/роутинга, а FSD-слои создадут избыточный бойлерплейт"*).
2. **Список слоев проекта**:
   - Описание назначения каждого слоя без использования шаблонных плейсхолдеров.
3. **Направленный граф зависимостей (DAG)**:
   - Явное перечисление допустимых потоков импортов (`A → B → C`) и запретов обратных импортов.
4. **Границы публичного API**:
   - Определение файла точки входа (например, `src/index.ts`) и состава его экспорта.
5. **Anti-Corruption Layer (ACL) и Валидация**:
   - Определение точек рантайм-валидации (схемы внешних данных, API, файлов).
   - Правила изоляции домена от внешних DTO/схем (мапперы, fallbacks, запрет просачивания DTO в UI).
6. **Отслеживание технического долга**:
   - Фиксация регламента учета техдолга в `docs/techdebt.md` (в коде `// TODO` запрещены).
