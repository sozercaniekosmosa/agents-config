# BaseTable: сопровождение компонента

Навык удерживает три артефакта компонента в согласованном состоянии: **код**, **конструктор**, **документацию**.
Изменение любого артефакта → обязательное обновление двух других.

## 1. Границы компонента (Scope Lock)

| Слой | Пути (от корня компонента) | Роль |
| --- | --- | --- |
| Код | `index.ts`, `types.ts`, `base-table.module.css`, `ui/**`, `lib/**`, `ui/__test__/**` | Рантайм-поведение и публичный контракт |
| Конструктор | `constructor/**` (entry, registry, dev-mode, presets, constants, view/**, генераторы) | DEV-редактор, превью и генерация TSX |
| Документация | `README.md` (RU, пользовательская), `guide.md` (EN, архитектурная спецификация) | Описание реального контракта и архитектуры |

Корень: `src/shared/ui/base-table`.
Все действия выполняются только внутри этого корня.
Внешние файлы не изменяются: нужна правка за пределами → остановка и вопрос пользователю.
`SKILL.md` — спецификация навыка, не артефакт компонента; правится только по прямому запросу.

## 2. Режимы вызова

### Режим A — `/base-table` без текста

Автосинхронизация по инструкции ниже.
1. Определить изменённые слои (git + анализ запроса).
2. Для каждого изменённого слоя применить матрицу синхронизации к двум остальным.
3. Изменений нет → выполнить полную сверку (`--check`), устранить только доказанный дрейф, ничего не выдумывать.

### Режим B — `/base-table <текст>`

Текст = задача. Агент фиксирует: работа относится к BaseTable, все действия — в рамках компонента.
1. Классифицировать задачу по слоям-источникам (что именно меняется: код / конструктор / документы) и сверить с эталонами (раздел 6).
2. Вопрос/уточнение без запроса на изменение → только ответ в чате, без правок и без матрицы.
3. Коллизия ориентиров/трактовок/требований → раздел 7: варианты + вопрос до правок.
4. Выполнить задачу.
5. Применить матрицу: затронутые слои → обновить остальные.
6. Требование задачи вне границ компонента → остановка и вопрос, без самовольного расширения scope.

## 3. Порядок выполнения

1. **Scope Lock**: зафиксировать режим, задачу, целевой корень.
2. **Baseline**: `node .agents/skills/base-table/scripts/base-table-sync.cjs --detect` (или `--base <ref>`).
   Явный слой из запроса добавляется к найденным git-изменениям.
3. **План**: составить список «источник → цели» по матрице. Цель без конкретного действия не принимается.
   Публичный API → пометить «соответствует эталону» либо «отклонение + строка в реестре 6.4».
   Коллизия → варианты и вопрос (раздел 7), не выбор по умолчанию.
4. **Исполнение**: изменять артефакты строго по чек-листам слоёв; соблюдать правила согласования.
5. **Верификация**: `--check`; при изменениях кода → `npx tsc --noEmit`; при изменениях `guide.md` → `node .agents/skills/guide/scripts/audit-guide.cjs src/shared/ui/base-table`.
   Тесты запускаются только с согласия пользователя.
6. **Отчёт**: источники → цели → файлы → результаты проверок.
7. **Feedback Loop**: см. раздел 11.

## 4. Матрица синхронизации

### 4.1. Изменился код → обновить конструктор и документацию

**Конструктор**
- Публичные props/types → поля редактора (`view/components/*-config*.tsx`), дефолты `presets.ts`, токены `constants.ts`.
- Новый/переименованный субкомпонент или prop → `preview-table.tsx`, `compact-generator.ts`, `expanded-generator.ts`, `helpers.ts`.
- Изменение вариантов/размеров/цветов → опции редактора и палитра; значения конструктора обязаны входить в рантайм-типы.
- Изменение поведения (выравнивание, editable, border, sticky) → превью и генерируемый TSX обязаны воспроизводить новое поведение.
- Изменение публичных экспортов `index.ts` → импорты конструктора и консольный API.

**Документация**
- README: таблицы API затронутых субкомпонентов, раздел адаптивности, особенности реализации, практические кейсы.
- `guide.md`: `architecture_map` (файлы), `feature_status`, `module_capabilities_and_contracts`, `architecture_and_constraints`.
- Новый файл/тест → строка в `architecture_map`; новый prop/поведение → README + контракты guide.
- Изменённые примеры должны компилироваться против нового API.

### 4.2. Изменился конструктор → обновить код и документацию

**Код**
- Каждое поле редактора обязано соответствовать реальному публичному prop; «фантомные» опции удаляются.
- Генерируемый TSX использует только публичный API и должен компилироваться.
- `presets.ts` / `constants.ts` → значения обязаны входить в union-типы рантайма.
- Консольный API (`toggle/enable/disable/status/list/edit/create`) и registry → поведение `dev-mode.ts` / `registry.ts`.
- Граница DEV-only (`import.meta.env.DEV` + dynamic import) сохраняется.

**Документация**
- README: раздел конструктора, перечень поддерживаемых props, команды консоли, ограничения (нет сохранения конфигурации).
- `guide.md`: `architecture_map` (файлы конструктора), `feature_status`, `module_capabilities_and_contracts`, `architecture_and_constraints`.

### 4.3. Изменилась документация → обновить конструктор и код

**Код**
- Каждый задокументированный prop/тип/поведение/пример обязан существовать и работать.
- Примеры README обязаны компилироваться и соответствовать публичному API.
- Документация описывает будущую функциональность → это изменение контракта: остановка и запрос подтверждения, а не молчаливая реализация.

**Конструктор**
- Задокументированный пользовательский prop/режим → элемент управления в редакторе либо явно зафиксированное намеренное исключение.
- Генератор обязан выдавать задокументированную каноническую форму (compact и expanded).
- Команды консоли и ограничения конструктора в README обязаны совпадать с реализацией.

## 5. Чек-листы слоёв

**Код**
- `types.ts` — единственный источник публичных типов; `index.ts` реэкспортирует всё публичное.
- Нет мёртвого кода, дублей и временных заглушек.
- CSS-переменные/классы существуют и используются.
- Тесты покрывают изменённое поведение; утверждения не ослабляются.

**Конструктор**
- Поле ↔ prop ↔ генерируемый TSX ↔ превью — сквозное соответствие.
- Палитра и пресеты валидны относительно union-типов.
- Compact и expanded генераторы изменены согласованно.
- Registry не течёт: регистрация/разрегистрация парная, позиции 1-based.
- Модалка и редактор не попадают в production-бандл.

**Документация**
- README: API-таблицы, адаптивность, особенности, кейсы, конструктор.
- `guide.md`: карта файлов без битых ссылок, статусы фич, контракты, архитектурные ограничения.
- Нет нереализованных обещаний; новые ограничения зафиксированы.
- Отклонения от эталона (раздел 6) → строка в реестре 6.4 + ограничение в `guide.md`; видимое поведение → ещё и README.
- README — RU, `guide.md` — EN, стиль «1 факт = 1 строка».

## 6. Эталонные ориентиры

Два внешних референса: Chakra UI Table — базовый (анатомия и оси API), Radix UI — дополнительный (имена вариантов, композиция, доступность).
Ориентиры не контракт: по умолчанию им следуют, отклонение допустимо, но обязано быть осознанным и записанным.
Приоритет: анатомия и оси → 6.1; имена, примитивы и a11y → 6.2; конфликт ориентиров → раздел 7.

### 6.1. Chakra UI Table — базовый baseline (P1–P7)

| # | Принцип | Как проверяется |
| --- | --- | --- |
| P1 | Составная анатомия: `Root`, `Header`, `Body`, `Row`, `ColumnHeader`, `Cell`, `ScrollArea` | новый субкомпонент встраивается в набор либо обоснован |
| P2 | Нативная семантика: `table/thead/tbody/tr/th/td`, `scope="col"/"row"` | нет div-эмуляции сетки, семантика не теряется |
| P3 | Ортогональные оси: `size` (sm/md/lg), `variant`, булевы режимы `interactive`, `striped`, `stickyHeader`, `showColumnBorder` | новое поведение → ось или флаг, а не набор ad-hoc пропсов |
| P4 | Style-props + респонсив-объект: `p/px/py/pt/pr/pb/pl`, `width/minWidth/maxWidth`, `{ base, sm, md, lg, xl }` | пропсы не дублируют CSS-свойства синонимами |
| P5 | Наследование с локальным переопределением: контекст задаёт дефолт, элемент переопределяет | `Row`/`Cell` переопределяют `interactive`/`justify` |
| P6 | Скролл-контейнер владеет overflow и внешней рамкой; таблица остаётся семантической | `ScrollArea` снаружи `Root` |
| P7 | Презентационность: сортировка/фильтрация/пагинация/виртуализация — не в компоненте | данные и состояние у потребителя |

### 6.2. Radix UI — дополнительный baseline (R1–R7)

| # | Принцип | Как проверяется |
| --- | --- | --- |
| R1 | `Root` владеет прокруткой: wrapper → scroll → `table` | вертикальный и горизонтальный скролл не разъезжаются |
| R2 | Variant-имена `surface`/`ghost`; плотность `size` — отдельная ось | новый визуальный режим → вариант, не набор флагов |
| R3 | `justify` (start/center/end) на ячейке и заголовке; вертикальный `align` — отдельная ось | горизонтальное и вертикальное выравнивание не смешиваются |
| R4 | `layout` (`auto`/`fixed`) — явная ось, а не скрытое решение | фиксация ширины объявлена, а не подразумевается |
| R5 | Заголовок строки — часть анатомии: `RowHeaderCell` = `th scope="row"` | первая колонка семантична, не декоративна |
| R6 | Принципы примитивов: композиция > конфигурация, `asChild`/Slot, `data-state`, порталы, controlled/uncontrolled, доступность | поведение собирается из частей и не теряет a11y |
| R7 | Респонсив — часть prop-контракта (`Responsive<T>`) | адаптивность объявлена в API, а не в CSS потребителя |

P6 и R1 расходятся по владельцу прокрутки → текущий гибрид: горизонталь в `Root`, вертикаль в `ScrollArea`; смена модели → коллизия (раздел 7).
`RowHeader` соответствует R5 (`th scope="row"`); у Chakra аналога нет — это не отклонение.

### 6.3. Политика отклонений

- Эталон — ориентир, не контракт; источник истины — рантайм-типы и реализация.
- Приоритет ориентиров: анатомия/оси → 6.1; имена/примитивы/a11y → 6.2; правила нет или ориентиры спорят → раздел 7.
- Отклонение допустимо, если: (а) даёт измеримую выгоду (перф, отсутствие layout shift, доменное требование), (б) не ломает P2 и P5, (в) зафиксировано.
- Фиксация: 1 строка в реестре 6.4 + ограничение в `guide.md` (`architecture_and_constraints`); видимое пользователю поведение → ещё и `README.md`.
- Молчаливое отклонение = дрейф → устраняется либо легализуется строкой в реестре.
- Паритет с эталоном не цель: API не расширяется только ради сходства.
- Новый проп/поведение без строки в 6.4 (или без явного соответствия baseline) → задача не завершена.

### 6.4. Реестр отклонений (текущее состояние)

| Отклонение | Причина |
| --- | --- |
| Стили: CSS Modules + CSS-переменные вместо slot recipes/CSS-in-JS | стек без runtime-стилей; токены дизайн-системы |
| `table-layout: fixed`; ось `layout` не выведена в prop | предсказуемые ширины; автоматическая раскладка запрещена |
| Нет вертикального `align` строки | вертикаль задаётся CSS; отдельная ось не востребована |
| Респонсив: CSS-переменные + media queries, брейкпоинты проекта | без JS-слушателей ресайза |
| Нет `Caption`/`Footer`/`ColumnGroup`/`Column`/`native` | не требуются в текущих сценариях; добавляются по запросу |
| Нет `asChild`/Slot, `data-state`, controlled-пропсов | композиция через контекст достаточна для текущих задач |
| Размеры sm/md/lg вместо 1/2/3 | читаемость и совместимость с дизайн-системой |
| Расширения: `ColumnHeaderIcon`, наследование `justify`, `bgColor/textColor/border/bold/link/editable` | доменные требования статусов и плотности |
| Sticky: `nth-child(n)` + `top` от высоты строки | CSS-only; предел 5 ярусов |
| Статусные рамки: inset `box-shadow` вместо `border` | исключить layout shift |
| `ScrollArea`: `maxHeight`/`overflowY`/`withBorder`; горизонтальный скролл в `Root` | Radix держит оба скролла в `Root`; разделение — осознанное |
| Цвета: токены по элементу вместо `colorPalette` | статусная семантика на уровне ячейки |

### 6.5. Место в процессе

- Режим B, шаг 1 → сверка задачи с 6.1 и 6.2.
- План → для публичного API: «соответствует эталону» либо «отклонение + строка в 6.4».
- Коллизия ориентиров → раздел 7: варианты и вопрос, не выбор по умолчанию.
- Верификация → `--check` проверяет структуру, соответствие эталону проверяется чтением диффа API.
- Реестр 6.4 — часть спецификации: правка только по прямому запросу пользователя.

## 7. Коллизии: решение принимает пользователь

Коллизия — ситуация, где допустимы ≥2 взаимоисключающих решения и выбор меняет контракт, архитектуру или поведение.

### 7.1. Когда это коллизия

- Ориентиры 6.1 и 6.2 дают разные ответы на один вопрос.
- Ориентир противоречит рантайм-контракту, `guide.md` или README.
- Требование пользователя противоречит ориентиру либо ограничению платформы.
- Задача допускает ≥2 равнозначных трактовки.
- Цена альтернатив сопоставима: доминирующего варианта нет.

### 7.2. Правило

- Агент не выбирает молча и не «голосует» большинством ориентиров.
- Агент готовит 2–3 варианта: что меняется (код / конструктор / доки), цена, риск, обратимость.
- Агент даёт рекомендацию и явно помечает её как рекомендацию.
- Работа останавливается до ответа пользователя.

### 7.3. Формат вопроса

`Контекст` → `Вариант A/B/C` → `последствия` → `рекомендация` → `вопрос`.
Ответ пользователя = решение; повторно не оспаривается.

### 7.4. После решения

- Архитектурное или контрактное → строка в 6.4 + ограничение в `guide.md`.
- Видимое поведение → `README.md`.
- Отчёт → «решение пользователя» + выбранный вариант.

### 7.5. Не коллизия

- Внутренняя механика без влияния на публичный контракт.
- Вопрос уже решён пользователем либо однозначно задан правилом/ориентиром.
- Тривиальный выбор в рамках утверждённого контракта.

### 7.6. Запреты

- Разрешать коллизию «по умолчанию», «по ближайшему ориентиру» или молча.
- Менять публичный контракт в обход вопроса.
- Начинать реализацию до ответа при коллизии.

## 8. Правила согласования

- Источник истины по фактам API — рантайм-типы и реализация; документация не может описывать несуществующий prop.
- Первичный артефакт — тот, который изменил пользователь. Остальные приводятся к нему, а не наоборот.
- Расхождение, требующее изменения публичного контракта, → подтверждение пользователя.
- Запрещено расширять компонент «попутно»: только задачи из запроса и их синхронизация.
- Нельзя подгонять документацию под баг: баг исправляется в коде, либо фиксируется как ограничение.
- Эталон (раздел 6) имеет приоритет над вкусовыми предпочтениями, но ниже рантайм-фактов и прямого запроса пользователя.
- Отклонение без строки в 6.4 → дрейф, а не архитектурное решение.
- Коллизия ориентиров, требований или трактовок → решение пользователя (раздел 7); агент готовит варианты.

## 9. Запреты

- Правки вне `src/shared/ui/base-table` без явного разрешения.
- Автозапуск `/check`, тестов, сборки и форматирования без запроса.
- `// TODO` в коде: техдолг → `docs/techdebt.md`.
- Дублирование контракта в трёх местах разными формулировками.
- Удаление/переименование файлов без обновления `architecture_map` и ссылок README.
- Изменение публичного API только ради паритета с эталоном без подтверждения пользователя.
- Новое отклонение от эталона без записи в реестре 6.4.
- Молчаливое разрешение коллизии и выбор варианта без пользователя.

## 10. Скрипт

`node .agents/skills/base-table/scripts/base-table-sync.cjs` — детекция изменений, матрица и сверка дрейфа.

- `--detect` (по умолчанию) — изменённые слои, цели синхронизации, инвентарь.
- `--detect --base <ref>` — изменения относительно ref (например, `HEAD~1`).
- `--detect --mode code|constructor|docs` — добавить слой из запроса.
- `--check` — дрейф: обязательные файлы, карта guide, компоненты/API в README, варианты и токены конструктора относительно рантайм-типов.
- `--json` — машиночитаемый вывод. Код возврата: 0 — расхождений нет, 1 — дрейф, 2 — компонент не найден.

## 11. Петля эволюции навыка (Feedback Loop)

1. После задачи оценить: выявлены ли новые правила синхронизации или пробелы чек-листов.
2. При пробеле → предложить точечное изменение `SKILL.md` (по подтверждению пользователя).
3. Зафиксировать запрос и трение: `node .agents/skills/observer/scripts/observer.cjs --record "<intent>" base-table "<friction>"`.
