# 🏭 Навык CEMIS (Система экологического мониторинга: ГТЭС и Насосы)

Вся логика и правила работы с подсистемой CEMIS разделены на узкоспециализированные спецификации. **При необходимости работы с кодом CEMIS агент обязан изучить соответствующую спецификацию по ссылкам ниже.**

## 📚 Спецификации (spec/)

- 🏗 **[Архитектура и UI-Правила](spec/architecture-and-ui.md)**
  - FSD-слои (Page, Widgets).
  - Управление состоянием (URL-Driven State `?unit`, `?pumps`).
  - Хаки UI (Chart.js, SVG, скругления, модалки).
  
- 📡 **[Потоки Данных (REST & SignalR)](spec/data-flow.md)**
  - Устройство хука `useCemisData`.
  - Приоритет данных (SignalR → REST).
  - Шаблоны свойств и маппинг по элиасам (Alias).

- 📜 **[Контракты и API](spec/contracts.md)**
  - Идентификаторы моделей и прототипов (`CEMIS_MODEL_ID`).
  - Логика построения меню и фильтрации узлов.

## 🛠 Встроенные Скрипты (Tools)
Агент ОБЯЗАН использовать утилиты ниже через `run_command` для авто-валидации своих решений:
- `node .agents/skills/cemis/scripts/validate-ui-rules.cjs` — **Обязательно** после любых правок в `.tsx` файлах `widgets/cemis-*`.
- `node .agents/skills/cemis/scripts/check-contracts.cjs` — **Обязательно** при изменении API, алиасов свойств или swagger-файлов.
- `node .agents/skills/cemis/scripts/data-diagnostic.cjs` — При жалобах на отсутствие данных или поиске багов (генерирует отчет `cemis-diagnostic-report.md`).
- `node .agents/skills/cemis/scripts/bug-report.cjs` — При возникновении нестыковок в API. Собирает данные и формирует MD-файл вопроса к команде в `bugs-report/[date-short-desc].md`.

## 📝 Инструкция для ИИ
- Строго использовать элиасы свойств, избегать хардкод GUID'ов.
- Правки UI выполнять в слое `widgets/cemis-*`.
- Исключить любые спекулятивные изменения в `src/pages/cemis/guide.md` — это read-only документация.
- Любые варианты и списки выбора, предлагаемые пользователю, обязательно нумеровать.
- **Формирование баг-репортов**: При составлении вопросов к команде бэкенда через `bug-report.cjs` (или текстом) запрещено предлагать варианты со скрытием UI-компонентов из-за нехватки данных. Если элемент заложен в дизайне, вопросы должны фокусироваться исключительно на получении корректных элиасов/данных от API (например: "Какой элиас использовать для общей мощности?").

## 🔄 Петля Эволюции Навыка (Feedback Loop)
- **Цель**: Непрерывное улучшение навыка без деградации. Отслеживание правок, вносимых как агентом в код, так и пользователем (в том числе в сами спецификации навыка), для приведения связанных концепций в соответствие.
- **Действие**: При завершении задачи или при выявлении концептуальных правок от пользователя агент **ОБЯЗАН**:
  1. Проанализировать, затрагивают ли изменения глубинные концепции навыка, и сформировать список необходимых корректировок спецификаций.
  2. Запустить проверочные скрипты `check-contracts.cjs` и/или `validate-ui-rules.cjs` для подтверждения, что изменения кода не ломают текущие правила (если менялся код).
  3. Явно предложить пользователю внести правки в базу знаний: предложить команду `/learn` ИЛИ запросить прямое согласие в чате (например: *"Да, согласен, вноси"*).
- **Аудит**: Обновление базы знаний (`spec/*.md`) выполняется строго под контролем пользователя.
