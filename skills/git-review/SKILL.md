# Навык Git Review

Превращает комментарии ревью в проверенные решения, а не в слепые правки.

---

## 🔑 Ключевые Принципы

1. **Доказательность**: замечание проверяется по коду (`файл:строка`), а не принимается на веру.
2. **Разделение типов**: баг, регрессия, контракт, стиль, вопрос, похвала и вкусовое → разные ответы.
3. **Минимальный патч**: одна правка = одна причина; соседний код не переписывается.
4. **Прозрачность**: в ответе → что проверил, что решил, как проверить.
5. **Скоуп**: сопутствующие изменения фиксируются в описании PR отдельным блоком.
6. **Безопасность**: push, публикация и резолв тредов → только после подтверждения пользователя (CFON).
7. **Approval-политика**: системные approval отключены → `sandbox_permissions` не запрашивать; команда упала по доступу → стоп + отчет.

---

## 🧷 Контекст проекта (источник истины)

- **Репозиторий**: `atmus-gpna/GPNA.ISGTM-UI`, база PR → `develop` (push в `master` и `develop` запрещен hook-ом).
- **Стек**: React 19 + TS strict + Vite 7; TanStack Query (server state) + Zustand (UI state); Zod 4 + RHF; `@willykit-ui/*`.
- **FSD**: `app → pages → widgets → features → entities → shared`; импорт только вниз; межслайсово — только через `index.ts`; `feature` !импортирует `feature`; `entity` !импортирует `entity`.
- **ACL**: DTO не покидают `entities`; мапперы `entities/*/model/*.mapper.ts` с safe defaults; валидация на границе (Zod-контракты).
- **Гейты**: `npm run build` (`tsc -b`), `npm run lint`, `npm run fsd`, `npm run check:deps:all`, `npm run test` (vitest), `npm run doctor`.
- **Тесты**: Vitest — только чистая логика (мапперы/парсеры/хелперы); E2E — `tests/integration/*.spec.ts` (Playwright); unit-тесты React-компонентов запрещены.
- **Правила**: `AGENTS.md`, `docs/project-rules.md`, `docs/arhitecture.md`, `docs/anti-corruption-layer.md`, `docs/authorization.md`, `docs/techdebt.md`.

## 📥 Вход

- Номер PR и репозиторий; если не заданы → определить по текущей ветке (`gh pr view --json number,baseRefName,headRefName`).
- Описание PR, diff (`gh pr diff <n>`), список файлов (`gh pr view <n> --json files`), связанные issue.
- Базовая ветка `develop` и head PR; зафиксировать head-коммит.

---

## 📋 Порядок Выполнения

### Шаг 1. Контекст

1. Прочитать правила проекта и архитектурные документы (`docs/`, `AGENTS.md`, `.agents/AGENTS.md`).
2. `gh pr view <n> --json number,title,body,baseRefName,headRefName,files,commits,labels`.
3. `gh pr checks <n>` → статус CI и какие job падают.
4. Зафиксировать head-коммит: `git rev-parse HEAD` и `git log --oneline develop..HEAD`.

### Шаг 2. Сбор комментариев

1. Inline-треды: `gh api repos/atmus-gpna/GPNA.ISGTM-UI/pulls/<n>/comments --paginate`.
2. Ревью-саммари: `gh api repos/atmus-gpna/GPNA.ISGTM-UI/pulls/<n>/reviews --paginate`.
3. Общие комментарии: `gh api repos/atmus-gpna/GPNA.ISGTM-UI/issues/<n>/comments --paginate`.
4. Сохранить: id треда/комментария, файл, строку, автора, текст, `in_reply_to_id`.
5. Ничего не отвечать до верификации.

### Шаг 3. Классификация

| Тип | Признак | Действие |
|---|---|---|
| Баг / регрессия | воспроизводимый сценарий | патч + тест |
| Контракт / тип | nullable, неверная сигнатура, DTO в UI | патч + тест |
| Архитектура FSD | кросс-импорт, deep import, слой не тот | патч или обоснованный отказ |
| Стиль | читаемость, нейминг, отсутствие RU JSDoc | патч или обоснованный отказ |
| Вопрос | «почему так?» | ответ с доказательством |
| Похвала | подтверждение решения | короткий ответ, код не трогать |
| Вкусовое | «я бы сделал иначе» | аргумент + решение пользователя |

### Шаг 4. Верификация (обязательна для каждого замечания)

1. Найти все вызовы; проверить, **достижим ли** сценарий из замечания (grep по слоям, маршрутам, MSW-хендлерам).
2. Проверить контракт: кто гарантирует не-`null`, где Zod-валидация, что делает маппер при пустом ответе.
3. `git log -S "<символ>"` → когда и зачем появился код.
4. Проверить слой: `entities` → только GET/данные; `features` → только мутации/действия; `widgets` → без доменной логики.
5. Для правки документации: битые ссылки, входящие ссылки, дата обновления, наличие замены.
6. Сформулировать вердикт: **обоснованно / частично / необоснованно** + причина.

### Шаг 5. Решение

1. При неоднозначности → 3 варианта + рекомендация.
2. Согласовать с пользователем до правок (CFON).
3. Одна правка → один коммит → один ответ в треде.

### Шаг 6. Патч

1. Минимальный дифф; без попутного рефакторинга и без переименований «заодно».
2. Тест на новое поведение: Vitest для чистой логики (мапперы/контракты/хелперы).
3. UI-изменение → правка/дополнение `tests/integration/<domain>.spec.ts`; unit-тест React-компонента не добавлять.
4. Проверки (точечно, без полного suite):
   - `npx tsc -b`
   - `npx eslint --no-cache <changed_files>`
   - `npx vitest run <path>`
   - при архитектурной правке → `npm run fsd`, `npm run check:deps:all`
5. Прогон тестов — только по согласию пользователя (`AGENTS.md`); hook-и не обходить.

### Шаг 7. Коммиты

1. Conventional Commits: `<type>(<scope>): <Описание> (#<issue>)`; `type` ∈ commitlint `type-enum`.
2. RU, заглавная, пассивный перфект (Исправлен/Добавлен/Обновлён/Удалён), ≤72, без точки.
3. Без `Co-Authored-By:` (hook `.husky/commit-msg` вырезает).
4. При блокировке hook-ов средой → ручные проверки (`tsc -b`, `eslint`) и сообщить пользователю; `--no-verify` не применять без явного разрешения.

### Шаг 8. Ответы в тредах

Шаблон:

```
Проверил: <факт 1>, <факт 2>.
Вердикт: <обоснованно / частично / необоснованно>.
Сделал: <что изменено, файл>.
Проверка: <как убедиться>.
```

- Похвала → «спасибо, подтверждаю» + 1 факт.
- Отказ → аргумент и альтернатива, без спора.
- Публикация: `gh api repos/atmus-gpna/GPNA.ISGTM-UI/pulls/<n>/comments/<comment_id>/replies -f body="<текст>"`.
- Резолв треда: `gh api graphql -f query='mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}' -f id="<thread_id>"` — только после подтверждения пользователя.
- Ссылки на коммиты → после push.

### Шаг 9. Отчет

1. Таблица: комментарий | вердикт | действие | ссылка.
2. Что осталось: CI (`gh pr checks`), резолв тредов, скоуп PR, обновление описания PR.
3. Какие замечания требуют решения пользователя.

---

## 🚩 Красные Флаги

- «Устарело» без списка конкретных расхождений.
- Патч без теста (для чистой логики) или тест, подогнанный под новое поведение.
- Ответ «исправил», когда правки нет в PR.
- Смешивание задач в одном PR без фиксации в описании.
- Ответ до верификации замечания.
- Правка `src/generated/**` или `dist/**` вручную.
- `// TODO` в коде вместо записи в `docs/techdebt.md`.

---

## ⛔ Ограничения

- Не пушить, не публиковать и не резолвить треды без подтверждения.
- Не менять и не отключать существующие ассерты.
- Не переписывать историю PR без явного запроса.
- Не запускать весь тестовый suite и `npm run build` «на всякий случай».

## 🔄 Петля Эволюции Навыка (Feedback Loop)

1. **Анализ сдвига**: новые типы замечаний, повторяющиеся ошибки ревью, пробелы шаблона ответа, изменения CI-гейтов.
2. **Фиксация**: при повторе паттерна ≥ 2 → предложить правку этого навыка; изменения гейтов (`package.json`, CI) → правка Шага 6 обязательна.
3. **Аудит**: `node .agents/skills/observer/scripts/observer.cjs --audit`.
4. **Лог**: `node .agents/skills/observer/scripts/observer.cjs --log-history git-review <trigger> <improvement>`.
